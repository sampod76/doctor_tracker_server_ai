The four list Services execute addSearch(), addFilters(), addDateRange(), and build() with the model's generated WhereInput. Searchable and sortable allowlists live in each module's constant file. Services define fixed inline Prisma selections, and Repositories only execute the supplied Prisma arguments. Client-controlled field selection is removed: fields, selectFields, selectedFields, and selectableFields are rejected as unknown query parameters. List response types are inferred from the fixed Service queries, and passwords and unselected relations remain excluded.

Both search and the existing searchTerm parameter are supported; search takes priority when both are present. Literal SQL LIKE escaping is retained. UUID filters use exact matching and the user ids parameter validates every comma-separated UUID. Invalid identifiers now return 400 rather than being silently ignored. Unknown filter properties, field-selection parameters, unsupported sort columns, invalid enums/booleans, and isDeleted overrides are rejected.

Pagination reuses calculatePagination and orderBy: page is 1–1,000,000 and limit is 1–100. Total count always uses the same where as the row query. fromDate/toDate filter createdAt in UTC, using the existing date formatter for inclusive end-of-day bounds. Either bound may be supplied; invalid dates and reversed ranges are rejected. Patient followUpDate and lastVisitAt retain their existing exact-date filters. No request timezone conversion convention was invented.

All list builders start with isDeleted=false and apply only explicitly supported filters. Existing route authorization remains unchanged. Seed lookups intentionally retain deleted records to detect conflicts. No tenant or ownership restriction existed in the previous list implementations; this change does not remove or invent one. Authentication password queries remain dedicated internal reads, and API queries retain select/omit protections.

The unused BasicRequestQueryParams and parseSort implementations were removed. The unused user filter-picking constants were replaced by actual searchable/sortable allowlists, and the user controller now forwards the entire validated query. No generic query framework or middleware was added.

This follows the supported [Prisma migrate diff workflow](https://www.prisma.io/docs/orm/v7/reference/prisma-cli-reference). The SQL was reviewed, wrapped in transactions, and augmented with each table's existing collation/check constraints that Prisma schema syntax does not represent. There are no invented tables or arbitrary splits. Prisma-generated UUIDs have no PostgreSQL column defaults, and no custom generator or intermediate legacy IDs remain in the rebuilt history.

Before replacing the local development history, read-only inspection verified DATABASE_URL points to localhost, NODE_ENV is development, the target contains no application tables or foreign keys, and \_prisma_migrations does not exist. Therefore no existing records or applied migration checksums conflict with this replacement. The four obsolete local migration SQL files and their empty directories were removed. A full recovery snapshot is retained at C:/Users/sampod/AppData/Local/Temp/doctor-tracker-query-builders-XpLFGK.

The configured application database remains untouched. No database reset, drop, truncate, or db push was run. The new history was deployed only to a freshly created local database whose name ends in \_test. This is a replacement history for the verified empty development target; an environment that used older history must retain or explicitly reconcile its applied migration history before deployment.
